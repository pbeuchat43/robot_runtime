# Live ROS parameter slice

Declared parameter inspection and live edits use the same manager, CLI, and authenticated browser as runtime/service commands. Provider validation remains authoritative. Hardware integration, startup configuration saving, and performance tuning require their own scope.

## Selected behavior

- Profiles optionally declare up to twelve parameter-node capabilities, each binding one exact node to an owned runtime unit and up to sixteen exact parameter names with explicit write permissions. Existing schema-1 profiles remain valid without the new optional `parameters` field.
- Public inspection calls the node's standard `GetParameters` and `DescribeParameters` services only when requested. It never starts a workload. One bounded refresh is shared by concurrent readers of the same capability; other requests receive busy, with no queue. Each capability allows at most one refresh start per second. There is no parameter-event subscription or background parameter polling.
- Read results include ROS types, values, descriptions, constraints, ranges, read-only/dynamic-typing flags, run/generation, original receipt age and a snapshot identity. Re-reading unchanged data preserves that identity. Values become stale; a reconnect does not refresh their age.
- The wire supports bool, signed 64-bit integer, double, string, and byte/bool/integer/double/string arrays. Integers and integer range bounds/steps use decimal strings. Arrays have at most 128 elements, strings 4096 characters, descriptions/constraints 1024 characters, and a complete parameter result at most 16 KiB. Oversized/invalid results fail explicitly. These bounds do not bound memory allocated inside DDS for incoming responses.
- Edits preserve the current ROS type, including for dynamically typed parameters. Unset/uninitialized values can be displayed when the provider returns them, but declaring, deleting or changing a parameter's type is outside this slice. Startup-only parameters must be exposed with `write: false`.
- A write carries a request UUID, config revision, expected run, worker generation, expiry and expected snapshot. The manager checks permission/type/freshness; the worker re-reads values/descriptors and rejects changes detected since inspection before using `SetParametersAtomically`. There is no fallback to non-atomic writes. One ROS mutation or parameter inspection runs at a time; no automatic retry or mutation queue exists.
- The final supervisor/expiry authorization happens immediately before the atomic set call. Graph node/service checks constrain routing but do not authenticate an OS process. The pre-write comparison cannot provide compare-and-set against external ROS writers: another writer can still race after it.
- Provider acceptance/rejection is durably recorded separately from readback. An accepted write is followed by reading the changed parameters; observed values may differ from the request. Readback failure does not erase a received acceptance. Mutation timeout/lost acknowledgement is uncertain, never replayed, and blocks further ROS writes for that run until local acknowledgement or a new run.
- Mutations invalidate cached parameter baselines for that runtime unit. Browser drafts remain explicit edits; they are not silently rebased onto new values. Reads are public; writes and operation-result access use the existing HTTPS session, Host/Origin and CSRF checks. Arguments are not retained in durable history.

## Verification boundaries

Use native Jazzy synthetic fixtures on `jah` for all parameter types, readonly/range metadata, provider validation and atomic rejection, shared reads, stale/run/generation/permission rejection, external-change conflicts, readback mismatch/failure, timeouts, no replay and manager/worker recovery. Exercise the real browser plus CLI against an installed wheel, including multiple clients and session enforcement. Existing deployments require a separate maintenance scope.

Primary references: [Jazzy parameter service implementation](https://github.com/ros2/rclpy/blob/jazzy/rclpy/rclpy/parameter_service.py), [parameter value interface](https://github.com/ros2/rcl_interfaces/blob/jazzy/rcl_interfaces/msg/ParameterValue.msg), and the project's [integration contract](integration-contract.md#ros-providers-and-live-parameters). Implementation uses the installed ROS services rather than copying their implementation.
